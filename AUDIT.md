# Larkvine marketplace audit and upgrade log

Audit started 2026-09-29. Severity: P0 critical, P1 high, P2 important, P3 polish. Findings below are based on repository code and local checks; production behavior and data have not been verified.

## Phase 0 — repository and system discovery

**Inspected:** application routes and components under `src`, Prisma schema and SQL migrations, package scripts and lockfile, Cloudflare/Next configuration, environment variable example, deployment notes, and existing issue/testing guides. Read the installed Next.js 16 route-handler and authentication guides before code changes.

**System map:** Next.js 16 App Router, React 19, TypeScript, Tailwind 4. Server-rendered pages plus client components. Route handlers and server actions form the backend. Prisma 6 with the D1 adapter uses Cloudflare D1 (SQLite); some checkout and stock operations use direct D1 SQL. NextAuth 5 beta credentials and JWT sessions handle login. Roles are string values (`customer`, `vendor`, `admin`), with store ownership checked in `requireStore()`. Product/store media uses Cloudflare R2. Cart uses persisted Zustand in browser localStorage. Deployment targets Cloudflare Workers via OpenNext, with R2 cache and a Durable Object queue binding. Resend is used only for password reset email. No configured payment gateway, payout provider, notification queue, analytics service, or test runner was found. Order payment is arranged manually between the customer and vendor through WhatsApp.

**Customer routes:** `/`, `/shop`, `/shop/[slug]`, `/search`, `/stores`, `/[store]`, `/[store]/[product]`, `/cart`, `/checkout`, `/order-confirmation/[id]`, auth pages, and `/account/profile`. Search and cart APIs, order creation, image serving, auth APIs. No customer order-history, wishlist, review, notification, or address-book route found.

**Vendor routes:** `/sell` onboarding; `/admin/dashboard`, `/admin/products`, `/admin/categories`, `/admin/orders`, `/admin/discounts`, `/admin/store`. No dedicated variants, fulfillment tracking, customer management, financial ledger, payouts, reviews, messages, or staff routes found.

**Platform admin routes:** `/admin/applications` and `/admin/stores` for store approval, suspension, verification, and deletion. No platform order/payment/refund/payout/dispute, audit-log, role-management, or report routes found.

**Data model:** User, Store, PasswordResetToken, Category, Product, Order, OrderItem, DiscountCode. Store-scoped products/categories/orders. An order belongs to one store, so multi-vendor checkout creates one order per vendor. No parent order, payment, refund, commission, payout, review, wishlist, address, notification, or audit-log tables. Money is represented as SQLite `Float`. Sizes/colors/images and measurements are serialized JSON strings. SQL migration `0004` has a trigger that decrements stock on OrderItem insert and rejects insufficient stock. Migration `0005` adds store tenancy. These existing migrations were inspected without applying them to production.

**Phase result:** discovery complete for the checked-in system. Deployment bindings were identified from configuration, not verified against production. No implementation changes in this phase.

## Continuation — cancellation concurrency verification (2026-09-29)

**Inspected:** migration `0012`, the vendor `updateOrder` server action, the existing cancellation regression test, and Cloudflare's D1 documentation. Cloudflare documents that one D1 database processes queries one at a time and that `batch()` runs statements as a transaction with rollback on failure ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)). The cancellation stock increment is a trigger within a single guarded `UPDATE`, so duplicate writes cannot observe a separate restock step.

**Verification:** Two separate Wrangler processes sent the same guarded cancellation update simultaneously to a synthetic local D1 order. The order ended `cancelled`; stock moved from 2 to 3 once. A second local fixture received concurrent cancellation and shipping updates; it ended `cancelled` with stock restored once. These are local D1 SQL tests, not authenticated server-action or production tests. Added worker-thread regression tests using two SQLite connections to a file: simultaneous cancellation returned one changed row and one no-op; a cancellation racing a shipping update ended cancelled with one restoration. `npm test`: 3/3 pass. Retry after a cancellation is a no-op. No customer cancellation flow exists in the checked-in route inventory. D1's single-database serialization does not eliminate application-level race conditions across separate reads and writes; the guarded one-statement transition and trigger enforce this invariant. A saturated D1 queue may return an overload error, so callers still need retry behavior.

**Status:** S6's at-most-one restoration invariant is verified in local SQL and automated SQLite concurrency tests. Authenticated action calls under concurrent requests and production behavior remain unverified. No production changes.

## PPR runtime diagnosis and CI hardening (2026-09-29)

**Method:** reproduced the mismatch under the production-representative `opennextjs-cloudflare preview` (workerd) against the current build; isolated it per route via the local observability API; one diagnostic non-minified build.

**Findings.**
- Affected routes: `/`, `/shop`, `/stores`, `/account/orders`, `/checkout`, `/search` — every **partial-prerender** route, all 200 and functional. `/cart` (static, non-PPR) is unaffected.
- React #419 source: `react-dom-server.edge.production.js` PPR resume check — `Expected the resume to render <Suspense> in this slot but instead it rendered <…>`. `<F>`/`<F2>` are minified names; React expected a `<Suspense>` boundary and got a different element, then recovered by client rendering.

## Order lifecycle and abandoned-inventory audit (2026-09-29)

**Scope:** audit and design only. No application, schema or production change. Detail: `docs/ORDER-LIFECYCLE.md`.

**Current state machine.** Creation status is `sent_to_whatsapp` (set by `POST /api/orders`). Vendor/status changes go through the store-scoped compare-and-set `updateOrder` action, gated by `canTransitionOrderStatus`: `sent_to_whatsapp → pending|confirmed|cancelled`; `pending → confirmed|cancelled`; `confirmed → shipped|cancelled`; `shipped → delivered`; `delivered` and `cancelled` terminal. Stock is **reserved at creation** by the `0004` `OrderItem` insert trigger inside the same D1 batch; restored **exactly once** on first transition to `cancelled` by `0012`; `0015` blocks cancelling shipped/delivered; `0016`/`0017` enforce tenancy and eligibility. There is no `expired` status, no expiry field, no acceptance timestamp, no WhatsApp-handoff tracking, no customer cancellation, and no cron. `paymentStatus` is vendor-reported only.

**Failure mode.** Because the only release path is a vendor cancellation, an order the customer never completes holds stock indefinitely. It cannot be quantified from current data because no handoff event is recorded; production currently has 10 orders / 0 cancelled.

**Options compared** (docs/ORDER-LIFECYCLE.md §4): A reserve-until-cancel; B auto-expire; C reserve-on-confirm (**high oversell risk**); D short window + accept-or-release (B tuned). Recommended model **if** auto-expiry is chosen: Option D with a trigger-based atomic `expired` transition mirroring `0012`, a scope guard so only `sent_to_whatsapp`/`pending` can expire, a reopen guard, a `(status, createdAt)` index, and a per-child-order idempotent sweep.

**Design validation.** `tests/order-expiry-design.test.mjs` (8 tests, in-memory SQLite, not applied to production) proves the proposed triggers/sweep: at-most-once restore, idempotent repeated sweep, only-unconfirmed-can-expire, expired-not-reopenable + fresh stock required, multi-vendor isolation, and the accept/expiry and cancel/expiry races (5 iterations each). The tests caught two required refinements: the scope guard must exempt `OLD='expired'` (idempotent re-run), and customer cancellation must be status-eligible so a racing cancel after expiry matches nothing.

**Owner decisions required before any implementation** (docs/ORDER-LIFECYCLE.md §6): adopt expiry or keep A; window length and start point; handoff tracking; customer cancellation scope; vendor rejection reasons; keep/remove vendor payment reporting; explicit Accept; expired-order visibility. **No lifecycle code or migration is produced until these are answered.**

**Verification:** `npm test` 33/33 (8 new design tests); `tsc`/`lint`/`build`/`verify:deps`/`verify:worker-runtime` pass; `git diff --check` clean; `npm audit` unchanged. No deploy.
